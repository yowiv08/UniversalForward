# Reproducing UniversalForward CPU measurements

This console benchmark compares two already-built UniversalForward plugin DLLs in separate .NET 10 processes. All SSE input comes from generated byte arrays. The synthetic `https://benchmark.invalid` request supplies metadata to the logger; the benchmark never sends it over the network and does not use accounts, API keys, or real request content.

The console assembly is named `UniversalForward.Tests` to use the plugin's existing `InternalsVisibleTo` declaration. It references the supplied DLLs directly, without production project references. Both variants use the same `Router.Contracts.dll`.

Build the v0.3.8 and v0.3.9 plugin in separate checkouts with the .NET 10 SDK. The following PowerShell example uses sibling checkout directories; run from their parent directory:

```powershell
$repositoryUrl = 'https://github.com/yowiv08/UniversalForward.git'
git clone --branch v0.3.8 --depth 1 $repositoryUrl UniversalForward-v0.3.8
git clone --branch v0.3.9 --depth 1 $repositoryUrl UniversalForward-v0.3.9
dotnet build ./UniversalForward-v0.3.8/src/Plugins.UniversalForward/Plugins.UniversalForward.csproj -c Release
dotnet build ./UniversalForward-v0.3.9/src/Plugins.UniversalForward/Plugins.UniversalForward.csproj -c Release

$baselineBin = (Resolve-Path ./UniversalForward-v0.3.8/src/Plugins.UniversalForward/bin/Release/net10.0).Path
$fixedBin = (Resolve-Path ./UniversalForward-v0.3.9/src/Plugins.UniversalForward/bin/Release/net10.0).Path
& ./UniversalForward-v0.3.9/benchmarks/cpu/run-benchmarks.ps1 -BaselineBin $baselineBin -FixedBin $fixedBin
```

`-BaselineBin` and `-FixedBin` must each contain `Plugins.UniversalForward.dll`. `-ContractsBin` may be supplied explicitly and defaults to `-BaselineBin`; it must contain `Router.Contracts.dll`. If your build does not copy this contract assembly into the output, point `-ContractsBin` to the .NET 10 `lib` directory of the restored `Router.Contracts` 2.0.0 package or a compatible host build output. `-OutputDirectory` defaults to `artifacts/cpu-benchmarks` in the checkout containing the runner. Paths with spaces are supported by quoted arguments:

```powershell
./benchmarks/cpu/run-benchmarks.ps1 -BaselineBin '../baseline/bin/Release/net10.0' -FixedBin './src/Plugins.UniversalForward/bin/Release/net10.0' -ContractsBin '../contracts/bin/Release/net10.0' -OutputDirectory './artifacts/cpu-benchmarks' -ClaudeMax 5000
```

The runner builds only this benchmark executable, copies each plugin into its own output directory, runs both variants, checks every downstream output hash, and writes `baseline-results.json`, `fixed-results.json`, `benchmark-results.json`, and `benchmark-results.md` under the output directory. Assembly paths in JSON are relative to the results directory; assembly SHA-256 values identify the exact measured binaries. Bin and obj directories are also kept beneath the output directory. `-ClaudeMax 5000` omits the largest Claude case for a shorter run; Responses and journal cases still run.

Measured cases are:

- Claude Messages with 2,500, 5,000, and 10,000 text deltas of 100 characters. Streams contain message/content-block start, delta, stop, usage, and message-stop events, delivered in 16 KiB chunks.
- Responses with a single completed-event data line of exactly 1, 2, 4, and 8 MiB including SSE framing, delivered in 16 KiB chunks.
- Real `RequestLogCapture.Received` / `CapturedContent` reads of a 512 KiB Responses event in 512-byte chunks. Metadata setup, output buffers, and input generation occur before timing; timed work includes reading, completion metadata, and the store writer queue flush. The original incoming request body is null in both variants. The logger observes the same small synthetic request in each variant. The fixed logger intentionally saves no upstream request or response body.

Each case runs one warmup and three measured repetitions. GC is forced before each timed region. `GC.GetTotalAllocatedBytes(precise: true)` includes managed allocation on all threads, including the journal writer. SHA-256 verification runs after timing. Collector outputs are checked against independently constructed expected JSON; journal output is checked against the original input bytes. The runner also verifies equality across plugin variants and records every raw sample.

These isolated parser/logger microbenchmarks describe elapsed time and allocation traffic, not application-wide CPU percentages or upstream latency. Wall time varies with workstation activity, JIT compilation, and GC. Process CPU time has coarse timer resolution; allocated bytes measure traffic rather than retained heap size. The recorded v0.3.9 run used .NET 10.0.12 with workstation GC on a 20-logical-processor machine. Published measurements are in [docs/performance/v0.3.9](../../docs/performance/v0.3.9/benchmark-results.md).
